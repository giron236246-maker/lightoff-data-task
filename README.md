# 用分集群前置检查减少调度超时等待

我的判断：优先修正“把不同集群的风险当成同一种问题”的调度方式。三个集群的失败与陈旧节点状态强相关，华东集群的失败则集中在剩余显存低于 4 GB 的任务。建议先做可回滚的分集群前置检查，再用线上实验判断是否真正减少等待。

**交付内容：真实数据审计、63 组阈值的历史回放、可调用的前置检查函数、逐任务决策明细、情景收益与验证计划。没有接入生产调度器，未声称已经降低线上超时。**

## 2. 看到了什么，优先解决什么

### 陈旧状态风险依赖集群

| 集群 | 状态延迟 ≤20 分钟：失败/已回传 | >20 分钟：失败/已回传 |
| --- | --- | --- |
| 华北通用算力池 | 10/187，5.35% | 26/64，40.63% |
| 华南视频渲染池 | 4/177，2.26% | 31/69，44.93% |
| 西南音视频节点组 | 6/189，3.17% | 37/80，46.25% |
| 华东推理集群 | 28/207，13.53% | 3/64，4.69% |

华北、华南、西南合计：陈旧组 94/213（44.13%），新鲜组 20/553（3.62%），约 12.2 倍。华东的方向相反，因此不能把“延迟 >20 分钟”作为所有集群统一的高风险判定。[原始分组及 Wilson 95% 区间](outputs/cluster_staleness.csv)

### 华东应优先检查低显存

华东剩余显存 `<4 GB` 的 44 个已回传任务中，26 个失败（59.09%，Wilson 95% 区间 44.41%–72.31%）；`≥4 GB` 的 227 个中，5 个失败（2.20%）。[分组明细](outputs/cluster_vram.csv)

这是“应检查状态新鲜度、资源占用及资源预留机制”的证据，**不是已经证明心跳丢失或 OOM 的根因**。数据没有 node_id、节点心跳、显存需求、错误码、队列长度和重试链路；不能定位坏节点，也不能确认因果机制。华东陈旧组更低的失败率也不意味着陈旧状态有保护作用，可能有混杂因素。

### 为什么不先按任务类型或输入大小拦截

任务类型的整体失败率约 11.43%–18.42%，区分度弱于上面的集群交互；输入 >80 MB 的已回传样本只有 21 个，失败 7 个，样本较少且有潜在混杂。暂不把素材大小当成显存需求，也不为每种任务拟合复杂阈值。[类型表](outputs/task_type.csv)、[负载表](outputs/payload.csv)、[交互表](outputs/cluster_interactions.csv)

## 3. 做了什么

在 [policy.py](policy.py) 实现仅依赖派发时可见字段的函数：

```python
from policy import decide

# 使用实际任务字段调用；函数不读取 is_success
decision = decide(cluster_name, node_free_vram, dispatch_time, status_synced_at)
```

默认候选规则：

1. 华东：记录显存 `<4 GB`，返回 `RECHECK_AND_REROUTE`。
2. 华北、华南、西南：状态延迟 `>20 分钟`，返回 `RECHECK_AND_REROUTE`。
3. 其他正常记录返回 `PASS`，表示未命中本规则，不代表资源适配或节点健康已获保证。
4. 未知集群、缺失/非有限/负显存、非法/无时区/未来同步时间返回 `RECHECK`；已有一次自动重试则返回 `ESCALATE`，避免无限重试。

`4 GB` 是本数据上的华东风险阈值，**不是所有模型的最低显存要求**；任何 PASS 仍须经过现有的任务资源适配检查。例如其他集群显存为 0 不会触发这条统计规则，但应被现有资源检查挡住。

建议接入流程：派发前执行规则；命中时请求实时心跳与显存快照，结合任务实际显存需求做原子资源预留；确认不适配时，在健康且适配的节点间选择目标，只允许一次自动切流；无可用目标时进入有时限的队列并提示用户。**当前代码实现的是判断函数与历史回放，没有实现心跳服务、资源锁或真实节点切换。** 数据也不足以推荐某个具体替代节点或集群。

## 4. 阈值怎么选，怎么检查稳定性

- 前五天（9 月 1–5 日）：756 个唯一任务，727 个已回传，用于阈值选择。
- 后两天（9 月 6–7 日）：328 个唯一任务，310 个已回传，阈值固定后做时间复核。
- 候选状态阈值 `[5,10,15,20,25,30,40,50,60]` 分钟，华东显存阈值 `[0,2,4,6,8,10,12]` GB，共 63 组。
- 以题目成本 120/10 分钟，以及**假设**重试有效率 `q=50%`，最大化前五天已回传任务的情景净节省；并列时优先更少拦截，再按阈值升序固定排序。
- 最优选择为 `>20 分钟` 与 `<4 GB`。搜索过程见 [训练期完整搜索表](outputs/threshold_search_train_only.csv)。邻近的 20 分钟/6 GB 训练期净节省 3,290 分钟，选择值为 3,410 分钟，说明 4 GB 的精确边界仍需新数据确认。

**这是回顾性的时间稳定性检查。** 我在设计策略前已经查看全量分布，规则形态和集群例外也由这份数据启发，因此后两天不能包装成从未查看过的独立测试集，更不能用它证明因果收益。没有使用 task_id 或结果标签作为派发特征，也没有随机拆分让重复记录跨组。

## 5. 怎么证明可能有用

### 历史覆盖与代价

| 指标 | 前五天 | 后两天复核 | 全周描述性回放 |
| --- | ---: | ---: | ---: |
| 全部唯一任务 | 756 | 328 | 1,084 |
| 已回传任务 | 727 | 310 | 1,037 |
| 命中任务（含未回传） | 191 | 74 | 265 |
| 命中已回传任务 | 187 | 70 | 257 |
| 命中历史失败 TP | 88 | 32 | 120 |
| 命中历史成功 FP | 99 | 38 | 137 |
| 未命中历史失败 FN | 19 | 6 | 25 |
| 失败覆盖率 | 82.24% | 84.21% | 82.76% |
| 命中组历史失败率 | 47.06% | 45.71% | 46.69% |

全周命中 24.45% 的调度，覆盖 82.76% 的已知失败。137 个原本成功的任务也会多付一次检查/切流成本，这是明确代价，不是无损拦截。命中组失败率的 Wilson 95% 区间为 40.69%–52.80%；后两天为 34.57%–57.30%。区间只描述样本比例，不是线上收益置信区间。[逐任务决策](outputs/dispatch_decisions.csv)

### 成本模型与不可观测的重试有效率

设 `F` 为历史失败数，`TP` 为命中的历史失败数，`H=TP+FP` 为命中的已回传任务数。`q` 表示命中的历史失败中，经一次检查/切流能避免 120 分钟超时损失的比例，**本 CSV 不能估计 q**。

```text
基线等待损失       = 120 × F
策略情景等待损失   = 120 × (F - q × TP) + 10 × H
情景净节省         = 120 × q × TP - 10 × H
盈亏平衡 q         = 10 × H / (120 × TP)
```

把 10 分钟视作每次命中的额外成本，包括误拦成功；重试未奏效的失败仍付 120 分钟。还假设切流不额外引入新的失败，且目标容量足够。这里累计的是**任务分钟**，不是单个用户等待、系统墙钟时间或完整端到端耗时。

| 已回传样本 | q=0% | q=20% | q=50% | q=100%（理想上限情景） |
| --- | ---: | ---: | ---: | ---: |
| 后两天净节省，分钟 | -700 | 68 | 1,220 | 3,140 |
| 全周净节省，分钟 | -2,570 | 310 | 4,630 | 11,830 |

在 **q=50% 的假设下**，后两天等待损失从 4,560 降至 3,340 任务分钟，净节省 1,220（26.75%）；全周从 17,400 降至 12,770，净节省 4,630（26.61%）。这些数是可审计的情景计算，不能表述成已经节省。

全周盈亏平衡 q 为 17.85%，后两天为 18.23%；有效率低于该线时策略可能增加等待。若误拦的原本成功任务因切流额外失败，需再扣 `120 × r × FP`，其中 r 是额外失败比例；本回放尚未观测这一风险。

未回传任务不参与上表的已回传分母；全周有 8 个命中未回传任务，在 q=50% 情景下，若它们全部原本会成功，净节省为 4,550；若全部原本会失败，为 5,030。只是在同一成本模型下补齐未知标签的边界，不代表缺失随机或未来收益保证。[重试有效率敏感性](outputs/retry_effectiveness_sensitivity.csv)

### 为什么选分集群，而不是更宽泛地拦截

固定相同阈值及 q=50%，比较后两天的 310 个已回传任务：

| 策略 | 拦截已回传 | 覆盖历史失败 | 误拦历史成功 | 情景等待损失，分钟 |
| --- | ---: | ---: | ---: | ---: |
| 不拦截 | 0 | 0 | 0 | 4,560 |
| 全部拦截 | 310 | 38 | 272 | 5,380 |
| 所有集群状态 >20 分钟 | 82 | 26 | 56 | 3,820 |
| 所有集群状态 >20 分钟或显存 <4 GB | 109 | 32 | 77 | 3,730 |
| 分集群规则 | 70 | 32 | 38 | 3,340 |

在这个情景中，分集群规则覆盖与统一 OR 规则相同数量的失败，却少拦 39 个历史成功任务，少付 390 任务分钟。全量逐日结果见 [daily_policy_replay.csv](outputs/daily_policy_replay.csv)；仍需前瞻检验。[所有策略完整结果](outputs/policy_comparison.csv)

## 6. 上线验证与调度优化计划

1. **先影子运行**：只记录命中，不改变调度；补齐 node_id、状态版本、实时显存、任务显存需求、错误码、实际等待时间、重试前后关联 ID、切流目标和排队时长。确认低显存和陈旧状态的机制，而非仅看相关性。
2. **再做小流量对照实验**：按集群与任务类型分层，在独立节点池/时间块做随机切换对照，防止同一节点被两组共用而产生容量干扰；固定阈值与一次重试预算。记录实验分配及触发规则版本。
3. **主指标**：每个提交任务因调度失败和切流增加的实际等待分钟（含未回传任务的追踪），同时报告失败率、P50/P95 等待、误拦、切流成功率、目标集群容量和排队时间；未回传进入后续追踪，不删除。
4. **成功标准**：在预设观察周期和样本量下，实验组平均调度等待低于对照，差值置信区间上界低于 0；P95 等待与成功率不恶化。样本量应根据影子期实际方差和目标最小改善量计算，现有数据没有实际耗时，不能编造功效结果。
5. **回滚条件**：触发队列/容量保护、重试有效率不能越过成本盈亏线、或成功率/P95 等待出现预设恶化即停用。具体警戒阈值先由影子期基线确定。

长期调度优化：状态加 TTL、断连节点短暂熔断；对目标节点实行任务级显存需求检查与原子资源预留；使用带幂等键的有界重试；逐集群校准策略，避免把全部任务集中转移到某个集群。没有节点容量和服务时间数据，目前不设计具体的负载均衡权重。

## 7. 一键复现与文件导航

Python 3.12；从仓库根目录运行：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe evaluate.py
.\.venv\Scripts\python.exe -m unittest -v
```

其他系统可使用 `python evaluate.py`、`python -m unittest -v`。依赖版本见 [requirements.txt](requirements.txt)。改变 q 可运行 `python evaluate.py --retry-effectiveness 0.2 --out outputs_q20`；改变 q 会重新按训练期目标选阈值，因此比较固定默认规则的 q 敏感性，请直接看默认运行生成的敏感性 CSV。

- `evaluate.py`：从原始数据重算审计、分组、搜索、时间复核、成本敏感性和图表。
- `policy.py`：线上可复用的无标签判断函数，默认 20 分钟/4 GB。
- `outputs/summary.json`：所有主结论的机器可读数据与输入哈希。
- `outputs/dispatch_decisions.csv`：全部 1,084 个唯一任务的特征、历史标签、动作和理由。
- `test_policy.py`：阈值边界、混合时区、异常状态、重试预算测试，以及用标准库独立核对真实 CSV 的计数和收益算式。
- `analysis.py`：作答前准备的通用 CSV 结构检查工具，不承担本报告的业务计算。
- `AI_LOG.md`：关键提示词、AI 错误、修正与取舍。测试中的合成输入只用于软件检查，没有用于业务结论。

图表使用 Microsoft YaHei；其他系统未安装此字体时可能出现字体提示，CSV/JSON 数值不受影响。所有输出可由命令重建，无外部数据或在线服务依赖。

## 8. 尚未完成与取舍

我优先完成数据口径、可解释策略、误拦成本和收益边界，未做复杂预测模型或 Web 服务。只有七天数据，47 个结果未回传且可能非随机；没有任务级重试链路、节点标识或真实耗时，无法证明根因、去重后的独立性、替代节点容量及切流效果。选择阈值和规则后应冻结配置，在新一周数据及在线对照实验中验证，避免继续在同一份数据上追逐更高回放收益。

本版本为首次正式分析交付；作答前模板已替换为本报告。后续持续优化应在此记录具体变化与额外验证结果。
